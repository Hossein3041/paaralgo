5 Merge Sort
- Bisher wussten die Threads welche Aktionen zu machen sind, sowie welche Daten zu sortieren sind. Es wurden Subarrays im Voraus gegeben.
- Jetzt soll der Sortieralgorithmus Merge Sort nach Divide-and-Conquer arbeiten: Die Aufgabenpakete entstehen zur Laufzeit und während Laufzeit dynamisch einem freien Prozessor aus dem Pool zugewiesen

5.1 Exkurs: Sequentieller Merge Sort
- Pseudocode für den sequentiellen Merge Sort
/* Sort the subarray a[p:r] by using the sequential Merge Sort algorithm recursively */
// a: array
// p: Anfang des Arrays
// r: Ende des Arrays
// q: Mitte des Arrays,
public void seqMergeSort(int[] , int p, int r){
	if(p >= r) return;

	final int q = (p + r) / 2;

	seqMergeSort(a, p, q);
	seqMergeSort(a, q + 1, r);

	seqMerge(a, p, q, r);
}
/* Merge he already sorted subarrays a[p:q] and a[q + 1: r] into a single temporary array b[p:r]
and assign the content f b[p:r] back to a[p:r] */
// Wir hatten ursprünglich das array a[p:r]
// diese teilen sich zu zwei subarrays für linke und rechts Hälfte a[q + 1: r] und b[p:r] und werden sortiert
// diese beiden subarrays werden gemergt in ein temp-array b[p:r]
// und b[p:r] wird danach zu a[p:r] zugeordnet
public void seqMerge(int[] a, int p, int q, int r){
...
}

public static void seqMerge(int[] a, int p, int q, int r) {
        int leftSize = q - p + 1;
        int rightSize = r - q;
        int[] L = new int[leftSize];
        int[] R = new int[rightSize];
        for (int i = 0; i < leftSize; ++i)
            L[i] = a[p + i];
        for (int i = 0; i < rightSize; ++i)
            R[i] = a[q + 1 + i];
        int iL = 0, iR = 0, iK = p;
        while (iL < leftSize && iR < rightSize) {
            a[iK++] = (L[iL] < R[iR]) ? L[iL++] : R[iR++];
        }
        while (iL < leftSize) {
            a[iK++] = L[iL++];
        }
        while (iR < rightSize) {
            a[iK++] = R[iR++];
        }
    }

1. Wie lässt sich das Laufzeitverhalten des sequentiellen Merge Sort abschätzen?
T(n) = O(n log n)

2. Wie lässt sich dieser Code parallelisieren?

	seqMergeSort(a, q + 1, r);

Man kann diese beiden Aufrufe parallel gestalten, mit dem
Fork/Join-Framework
Und man kann seqMerge() parallel gestalten: parMerge()

Paralleler Pseudocode (1)

Klasse RecursiveAction ist eine abstrakte Spezialisierung von ForkJoinTask<Void>, für rekursive Divide-and-Conquer-Aufgaben
im Fork/Join-Framework. Wesentliche Punkte:

- Erweitert ForkJoinTask<Void>, implementiert Scheduling und Work-Stealing eines Fork/Join-Pools.
- Subklassen müssen coompute() implementieren
- compute()-Methode:
-> Enthält gesamten Divide-and-Conquer-Logik:
-> Problem in Teilaufgaben aufteilen und per fork() bzw. invokeAll() parallel starten.
-> Anschließend Ergebnisse per join zusammenführen

- Task-Steuerung
-> fork(): startet einen Teiltask asynchron im Pool
-> join(): wartet auf dessen Abschluss
-> invokeAll(taskA, taskB, ...): Shortcu für gleichzeitiges Fork & Join aller Tasks
-> exec(): interne Methode, die compute() aufruft und Ergebnis-Handling übernimmt.

Fazit: RecursiveAction bietet einen einfachen Einstieg in parallelisierte, rekursive Algorithmen ohne Ergebnisobjekte.
Man implementiert nur compute(), und das Framework kümmert sich um Scheduling, Lastverteilung und Synchronisation.

Wie könnte eine Implementierung von parMerge aussehen?

parMerge: Lösungsversuch (1)

Man schaue auf dem ersten Ansatz, den parallelen Merge-Sort durch Aufrufe von seqMerge zu realisieren.
In einer Idealwelt mit unendlich vielen Prozessoren ergibt sich für kritische Pfad-Laufzeit (Span):
T∞(n) = T∞(n/2) + c * n => T∞(n) = Θ(n)
D.h. das Mischen dominiert die Gesamtlaufzeit, genau wie beim Odd-Even-Merge-Splitting-Sort. Nur die Aufgabenteilung
in Form von leftTask und rightTask parallel zu gestalten reicht nicht, da der sequentielle Merge mit Θ(n) den kritischen Pfad bestimmt,
da die Laufzeit von der sequentiellen seqMerge() die Gesamtlaufzeit dominiert.

Wenn wir die Laufzeit bei paralleler Implementierung durch Parallelisierung verbessern wollen, müssen wir auch das Mischen parallelisieren.

parMerge: Lösungsversuch (2)

Es soll das Mischen von zwei Subarrays durch Divide-and-Conquer parallelisiert werden.

Aufgabe: Gegeben seien diese beiden subarrays a[p1:r1] und a[p2:r2]. Diese sollen in ein Hilfsarray b[p3:r3] gemischt werden,
wobei r3=p3+(r1-p1+1)+(r2-p2+1). Aber woher kommt p3 und welchen Anfang soll das darstellen?
Den Anfang von ersten Subarray, also p1? Ist p3 Äquivalent zu p1? Und welches Ende soll r3 darstellen?
Ist das da Ende von zweiten Subarray also r2? Ist r3 äquivalent zu r2?

Vorgehen: Die beiden Subarrays sollen jeweils durch ein Pivot-Element x in zwei Teile geteilt werden.
Dabei sind alle Elemente in den unteren Hälften höchstens so groß wie x bzw. alle Elemente in den oberen Hälften
mindestens so groß wie x.

Ziel: Das Mischen von zwei bereits sortierte Subarrays mittels Divide-and-Conquer parallelisiert werden.
Aufgabe: Gegeben sind zwei sortierte Bereiche:
- a[p1:r1]
- a[p2:r2]
Und ein Zielbereich
- b[p3:r3] mit r3 = p3 + (r1 - p1 + 1) + (r2 - p2 + 1).
Vorgehen:
1. Wähle Pivot-Element x
2. Teile beide Subarrays jeweils in untere und obere Hälfte, sodass
- in den unteren Hälften alle Elemten ≤ x sind,
- in den oberen Hälften alle Elemente ≥ x sind.
3. Nun entstehen vier Teilsegmente (zwei in jedem Subarray) und entsprechend zwei unabhängige Merge-Aufgaben für diese Paare.

parMerge: Wahl des Pivot-Elements:

Wähle q1 = [(p1 + r1) / 2] und x = a[q1], d.h. der Index q1 teilt das erste Subarray bezüglich des Pivot-Elements.

Wie findet man einen entsprechenden Index q2, der das zweite Subarray bezüglich des Pivot-Elements teilt?

-> Implementiere eine Methode findSplitPoint(x), die eine sequentielle binäre Suche auf dem (sortierten!) zweiten Subarray durchführt und q2 zurückliefert.

Anschließend mische rekursiv (und nebenläufig) die beiden linken bzw. die beiden rechten Hälften der jeweiligen Subarrays zusammen.

Nochmal:
- Pivot-Wahl: Index q1 = [(p1 + r1) / 2] im ersten Subarray, Pivot-Wert x = a[q1].
- Split im zweiten Subarray: Suche mittels binärer Suche auf dem sortierten Bereich [p2:r2]
die Position q2, an der x einsortiert würde.
- Rekursives, paralleles Mischen:
-> Merge von [p1:q1] mit [p2:q2]
-> Merge von [q1 + 1:r1] mit [q2 + 1:r2]
beides in unabhängigen Teilaufgaben.

parMerge: Gleichmäßige Lastverteilung?
- Die Pivot-Strategie liefert ausgewogene Teilaufgaben und verhindert eine Degeneration zu einem langen, sequentiellen Rekursionspfad:
- Annahme: Erster Bereich hat n1 Elemente, zweiter höchstens n2 ≤ n1; Gesamtgröße n = n1 + n2.
- Worst-Case einer Teilaufgabe: Man mischt immer die halbe Länge des größeren Bereichs n1/2 mit allen Elementen des kleineren, also
n1/2 + n2
- Schranke: 3/4 n
- Folgerung: Jede der beiden rekursiven Merge-Teilaufgaben hat höchstens 3/4 der ursprünglichen Elemente.
Damit schrumpft jedes Teilproblem um einen konstanten Bruchfaktor, und die Rekursionstiefe bleibt O(log n) -
es trifft also keine unkontrollierte Entartung auf.

Implementierung von findSplitPoint(x):
/**
* Finde im bereits sortierten Array-Bereich a[p2:r2] die Position q2,
* so dass a[p2:q2] ≤ x und a[q2+1:r2] > x (oder q2 = r2, falls alle Werte ≤ x).
*
* a: das sortierte Array
* p2: Startindex des Bereichs (inklusive)
* r2: Endindex des Bereichs (inklusive)
* x: Pivot-Wert
* return lo - 1: den größten Index q2 ∈ [p2:r2], für den a[q2] ≤ x
*/
private static int findSplitPoint(int[] a, int p2, int r2, int x){
    int lo = p2;
    int hi = r2 + 1;
    while(lo < hi){
        int mid = (lo + hi) / 2;
        if(mid <= r2 && a[mid] <= x){
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    return lo - 1;
}
Die Methode findSplitPoint durchsucht im bereits sortierten Teilbereich a[p2:r2] per binärer Suche die Stelle,
an der das Pivot-Element x einsortiert würde, und liefert genau den größten Index q2, für den noch a[q2] ≤ x gilt.
Dazu hält sie zwei Zeiger lo (anfangs p2) und hi (anfangs r2+1) im halboffenen Intervall [lo:hi).
In jeder Iteration wird die Mitte mid = (lo + hi) / 2 berechnet: Ist a[mid] ≤ x (und mid noch innerhalb von r2),
verschiebt sie lo auf mid+1, andernfalls setzt sie hi auf mid. Sobald lo == hi ist, zeigt lo auf die erste Position,
bei der ein Element größer als x stehen würde (oder sie ans Ende, wenn alle Werte ≤ x sind).
Der gesuchte Split-Index ist daher lo - 1. So erhält man in logarithmischer Zeit jenen Punkt, ab dem in zweiten Subarray
alle Werte strikt über dem Pivot liegen.

parMerge: Insgesamt
- Paralleles Mischen: Von a werden zwei Subarrays in einem Hilfsarray b zusammengemischt.
Dafür gibt es eine eigene RecursiveAction namens ParMergeAux, die nach Divide-and-Conquer-Prinzip arbeitet.
- Paralleles Zurückkopieren: Die gemischten Daten von b wieder zurück nach a kopieren. Dafür eine zweite RecursiveAction
namens ParCopy implementieren. Das Kopieren geschieht ebenfalls parallel über rekursive Teilaufgaben.

Laufzeit von Parellelen Merge Sort:

Wie ist die Laufzeit, vom parallelen Merge sort?

T(n) = T(n/2) + a * log(n)
- T(n/2) ist die Laufzeit für den rekursiven Abstieg
- a * log(n) ist die Laufzeit, wegen der binären Suche in findSplitPoint(), was ja logarithmisch läuft.
- Eingegeben in wolfram, bekommen wir als Ergebnis: T(n) = (log^2(n))

Was soll das heißen?

In den Buch steht:

First, let’s use work/span analysis to get some intuition for why we need a parallel merge procedure.
After all, it may seem as though there should be plenty of parallelism just by parallelizing MERGE-SORT without
worrying about parallelizing the merge. But what would happen if the call to P-MERGE in line 10
of P-MERGE-SORT were replaced by a call to the serial MERGE procedure on
page 36? Let’s call the pseudocode so modiûed P-NAIVE-MERGE-SORT.
Let T1(n) be the (worst-case) work of P-NAIVE-MERGE-SORT on an n-element
subarray, where n = r - p + 1 is the number of elements in A[p:r] and let T(n)
be the span. Because MERGE is serial with running time O(n), both its work and
span are O(n)/. Since the serial projection of P-NAIVE-MERGE-SORT is exactly
MERGE-SORT, its work is T1(n) = O(n log n). The two recursive calls in lines 5
and 7 run in parallel, and so its span is given by the recurrence

T(n) = T(n/2) + O(n)
     = O(n)

Wir sortieren einen Array der Länge n. Parallel-Merge-Sort führt
- Zwei rekursive Aufrufe auf Teilprobleme der Größe n/2 aus, welche sich sequenziell aufsummieren:
2T1(n/2)
- und anschließend einen parallelen Merge, der insgesamtg O(n) Vergleiche und Kopieren erfordert.
Damit ergibt sich die Rekurrenz
T1(n) = 2T1(n/2) + O(n)
und nach dem Master-Theorem
T1(n) = O(n log n)

Auf unendlich vielen Prozessoren bestimmt der längste Abhängigkeitsweg die Laufzeit. Wir haben
- die beiden Sortierrufe auf n/2 laufen parallel => Betrag T(n/2).

O(log n). Danach spawnen wir zwei Teil-Merges, aber nur einer trägt zum kritischen Pfad bei.
